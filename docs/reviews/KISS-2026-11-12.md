# KISS review, 2026-11-12

`main` at `c973f00`, after the fixes for REVIEW-FABLE5.2. Read against AGENTS.md: "Keep the structure; add mechanisms only for measured problems." Nothing in the code was changed for this review.

Four reviewers each read one part of the tree. A fifth pass checked their main claims: `golang.org/x/tools/cmd/deadcode` built from source, plus grep. `go vet ./...` is clean. `go test ./...` passes. I did not run `-race`, the live suite against DHIS2, the adversarial suite or the app's tests.

## Verdict

The core is lean, and the weight is in its breadth.

The storage, search and request code (`store`, `tracker`, `trackerapi`, `core`, about 17 000 lines) has no mechanism without a measurement behind it. Every cache, the SQL/Go split in searches, read-on paging, shared listings and the write lock each have a dated number in PERFORMANCE.md and a guard test. The sync loop is one linear list of steps. All in-scope items of KISS-2026-10-20 are fixed, except those kept by decision (item 6, the memory limit, "simulate uplink cut").

What makes the project large is how many places it runs and how many optional parts it has:

- three platforms: Pi, Windows and macOS;
- a TPM device key that no board has run;
- Wi-Fi and modem management that is untested on hardware;
- an mDNS responder that a Pi does not need;
- a USB stick restore;
- central moves;
- four ways to check that a save reached central;
- 6 800 lines of finished plans in `docs/superpowers`.

Each of these is a reasonable answer to a real question. Together they are about a third of the production code outside the core, and the parts that have had the least testing on real hardware. Review FABLE5.2 recommendation 14 says the same thing from the security side.

### Tests and CI

- **T1. CI does not run on push.** `test.yml`, `windows.yml` and `macos.yml` are `workflow_dispatch` only. Review FABLE5.2 recommendation 7 ("Turn on CI for every push") is not done, and the reason is the organisation's Actions budget. At least `go vet`, `go test ./...` and the app's `pnpm test`, `eslint` and `tsc` should run on push to `main`. That job takes a few minutes.
- **T2. The app is not tested in CI.** No workflow mentions `apps/`. The approval steps exist in Go and in TypeScript, and only the live `TestFacilityHubApp` checks that they agree.
- **T3. The fake central can drift from DHIS2.** The 193 e2e tests run only against the fake. The live and adversarial suites run against real DHIS2 only when someone runs `hubtest`. Nothing compares the fake with the recorded `testdata/2.42` answers. Run `hubtest` on 2.42 and 2.43 for every release, as AGENTS.md asks.
- **T4. `scripts/test-upgrade.sh`** repeats `TestG1…` to `TestG4…` in `internal/adversarial`, except one case: "a release whose signature could not be fetched is tried again". Move that case into `TestG3G4ReleasesRefused` and retire the script.
- **T5. Python drivers.** `control()` is defined five times and `login` three times across `clients/*.py`. Eleven Go call sites start them by hand. A `clients/common.py` and a Go `runClient` helper would remove 150–250 lines.

## Checked and justified

- **Storage and search:** the SQL/Go split in searches, read-on paging, the payload cache, `Viewer.memo`, prepared statements, the single write lock and the visibility bitmaps. Each has a number and a guard.
- **Shared listings and the hourly refresh:** central's requests fell from 53 000 to 9 400 a day per hub.
- **Push rules:** the 1-day limit, the 7-day wait for a login, the probe rules (D6, B1).
- **Proxy and local reads:** `revalidate` (Capture start 77 s to 1.1 s) and local reads (44 requests per visit to 2).
- **Clocks, signed instructions, store damage detection and the refusal pages:** each answers a recorded finding and is small.
- **Self-upgrade:** the image has no SSH, so this is the only way a fix reaches a hub.
- **The hub's certificate authority:** browsers refuse service workers on an untrusted certificate.
- **The Facility Hub app:** it calls central one way. It has no unused exports or components.
